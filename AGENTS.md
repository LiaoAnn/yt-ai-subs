# yt-ai-subs

Chrome extension (Manifest V3) that transcribes YouTube audio with a speech-to-text model and, optionally, translates it with an LLM, a few chunks ahead of the playhead, so it only spends money on what the viewer actually watches.

## How agents keep knowledge

- Do not use agent memory features (Claude memory, Codex memories, etc.). Anything worth remembering goes into the repo:
  - project decisions and conventions → this file;
  - repeatable procedures (testing in the browser, releasing, debugging the audio hook) → a skill under `.claude/skills/<name>/SKILL.md`;
  - rules that can be checked mechanically → a lint rule or a test, not prose.
- When a decision here changes, update this file in the same change.
- Work is split across t3 threads: a supervisor hands tasks out with the `delegate-to-thread` skill, and a delegated thread works and reports with `run-delegated-task`. A brief that keeps repeating the same instructions means they belong in a skill.

## Product decisions

- **Provider**: Groq first (Whisper `whisper-large-v3` / `whisper-large-v3-turbo` for speech-to-text, `openai/gpt-oss-120b` / `openai/gpt-oss-20b` for translation). OpenRouter / OpenAI are optional extras for translation. No xAI/Grok, no Codex subscription.
- **Groq free tier limits** (design the scheduler to stay under them):
  - Whisper: 20 requests/min, 2,000/day, 7,200 s audio/hour, 28,800 s audio/day, 25 MB per file.
  - gpt-oss-120b / 20b: 30 requests/min, 1,000/day, 8K tokens/min, 200K tokens/day.
- **Languages**: mainly Japanese and Korean sources, Traditional Chinese (Taiwan) target. Translation is optional: a transcribe-only mode must work on its own.
- **Where captions appear**: in YouTube's own caption (CC) menu as a selectable track ("AI 繁中", "AI 英文" or "AI 原文", named from the settings when the video loads; the player cannot rename it live: its track list is built once per video and neither its player response, a captions reload, reloading the captions module nor `updateVideoData` renames it (the last pauses playback), so the popup notes that a renaming save applies from the next video or reload), drawn by YouTube's renderer with the viewer's caption settings. The page script adds the track to the player responses of the videos the page asked for (`ytInitialPlayerResponse`; from `/youtubei/v1/get_watch` and `/player` via `fetch` only a response whose video is in the URL or named in the request body, which YouTube gzips: the page also gets made-up responses through `/player` with an empty request body and random IDs and titles such as `Kymdnr0KGWq`, and the captured pre-rolls (2 of 2) had no player response of their own), answers the player's timedtext XHR for it with our json3, selects it once per video, and reloads it when new cues arrive. During an ad (`ad-showing`) the page script's track control and health check follow the video in the URL rather than `getVideoData()` (which kept the main video's ID in the ads captured, but a wrong ID there would reset that video's health verdict and track state), and the content script keeps that video's state and says nothing (its debug reason is "廣告中"). The overlay is only the fallback, used per video when a health check sees the hook break; the popup shows which mode the tab uses. **Other extensions on `ytInitialPlayerResponse`**: an ad blocker (AdBlock, 2026-11-09; the user's `getOwnPropertyDescriptor` showed its `set(e)` method in place of our arrow setter) can redefine the property after our page script, so our setter never runs: no track, no creator-track check, no video length (the MediaSource waited the 5 s fallback, the content script 15 s for a creator answer, the health check 8 s; first caption 22–26 s after load in 2 of 2 simulated runs, 23.9 s at the user's). So the page script also reads the property whenever the parser adds an element (a `MutationObserver` until `DOMContentLoaded`: its records are delivered in the microtask checkpoint before the next inline script, the one that hands the response to the player) and patches the object in place whoever's accessor holds it, once per video; and once per video it checks the player's own copy (`movie_player.getPlayerResponse()`): without our track (a getter that hands out copies, a path we do not hook) the overlay is used at once ("AI 字幕軌沒加進播放器（…）") and, if the page never saw the response, its length, info and creator tracks come from that copy. Simulated with a test extension that redefines the property after ours (`set(e)`, the user's shape; fake Groq): before, first caption 26.1 and 32.1 s after the page script loaded (2 runs), and on Il3rOIG-6pg the creator's zh-Hant track was never seen, so Whisper and translation were paid for from 22 s on; after, the track was added at 0.6–1.0 s and the first caption came 5.3–6.8 s after load (W1iGWTlt_hU, 3 runs), Il3rOIG-6pg's creator track was selected at 2.4 s (1 run); with a getter that returns copies: overlay at 1.2 s, first caption 5.9–6.0 s (2 runs). How it works and how to debug it: the `debug-caption-track` skill.
- **Creator captions first** (`src/shared/creator-captions.ts`, `src/page/creator-hooks.ts`, `src/content/creator-source.ts`): the page script notes each player response's caption tracks before adding ours. (1) A creator-uploaded track (no `kind`) already in our track's language (zh-TW target: `zh-Hant*`, `zh-TW`, `zh-HK`, `zh-MO`; plain `zh` is ambiguous and does not count) while translating: our track is not added, the page script selects the creator's track once per video (the viewer can still switch), nothing is transcribed or translated, and the popup says "創作者上傳的字幕". Selecting beats a note: the viewer installed the extension to get these captions without doing anything, and a human translation costs nothing. (2) A creator track in the spoken language (the setting, or the automatic track's language for "auto"): it and YouTube's automatic track of that language are fetched, and if usable its lines replace Whisper's and are only translated, in 60 s chunks up to 120 s ahead (cache key `cache:<video>:creator:<language>:<translation>`; with translation off, nothing is called at all). Not usable, so Whisper as before: a copy of the automatic track (error rate under 0.1 and p90 of the line-start difference ≤ 0.1 s; hand-made text with YouTube-aligned timing has offset 0 but about 0.2 error rate, so both are required), a track covering under half of the automatic track's lines (summary cards), an empty or unfetchable track. Fetching needs the player's `pot` token: the player adds it only to URLs that look like a real track's, so our track's baseUrl copies a real track's parameters, and the token from the player's request for our track fetches any track of the video. The content script schedules nothing until the page script has answered (at most 5 s ad-free without an answer, 30 s while fetching; the page script knows within about a second of the first audio, from the player response or the player's own copy, so 15 s, the old limit, was only ever spent when the page had missed the response). Like the track name, the choice is made once per video from the settings at load (the player cannot change its track list live); a settings save that renames the track says so in the popup. Translation prompts get a rule for caption cards (`[…]`, `(…)`, `【…】`) and speaker labels (`name / …`, `name：…`) only when a line has one.
- **Audio source**: copy the audio YouTube already appends to its MediaSource buffers (hook `SourceBuffer.prototype.appendBuffer` in the page's MAIN world). Never download media from googlevideo directly. Appends do not follow WebM element boundaries: `AudioStore` (`src/content/audio-store.ts`) searches for cluster headers in the last 40 bytes of the previous append plus the new one, so a header split across appends still starts its own cluster; an append that itself starts with a whole cluster header (a seek) is never joined to the previous tail. Never an ad's audio (`src/page/media-source-kind.ts`): an ad gets its own MediaSource on the same `<video>`, and `ad-showing` on `#movie_player` is not a safe clock (it was still set when the main video's MediaSource was created after a pre-roll, in 2 of 2 captures), so each MediaSource with an audio SourceBuffer is classified and its segments are held back until then: "main" when its `duration` is within 2 s of the URL video's `lengthSeconds` (YouTube sets it before the first append; an ad's duration is its own length; the length comes from the player responses the page saw, else from `movie_player.getPlayerResponse()` when its video is the URL's) and, if it was seen during an ad, once `ad-showing` clears while it is still the `<video>`'s source (an ad exactly as long as the video is detached instead, and counts as an ad); "ad" when the duration differs and `ad-showing` was seen while it was the `<video>`'s source; after 5 s without either (no length known) the old per-append rule (drop while `ad-showing`). The state and the held segments live in `MediaSourceGate`.
- **Only while someone watches** (`src/content/watching.ts`): no new chunk is sent during an ad or while the tab is hidden (`document.visibilityState === "hidden"`: a background tab, and in Chrome also a minimised window); requests already at Groq finish, a chunk still decoding is dropped before it is sent, and scheduling resumes from the playhead when the tab is shown again (the audio played meanwhile is not transcribed). A hidden tab whose video is in picture-in-picture (`document.pictureInPictureElement` or a Document Picture-in-Picture window) counts as watched; a hidden tab that only plays the audio does not, so autoplay-next in a forgotten tab spends no quota.
- **AI-dubbed audio: do nothing** (`src/page/audio-track.ts`): YouTube adds AI dubs to some videos and in an English browser plays the English dub by default (17 of the 48 eval videos on a fresh profile; in a `--lang=zh-TW` profile 0 of 4 dubbed videos did: none offers a Chinese dub). Someone listening to the dub does not need our captions, and Whisper would hear English. So while `movie_player.getAudioTrack()` is a dub (its inner part's `isAutoDubbed`, else `acont=dubbed-auto` in the base64 xtags of its `id`), the page script passes on none of its audio (checked at every append), selects neither our track nor the creator's and fetches no creator track, and says `dubbed` in `caption-mode`; the content script sends nothing (requests in flight are cancelled, its stored audio, the original's, is kept), no status shows on the player, and the popup says "AI 字幕暫停（正在播放 AI 配音音軌，切回原始音軌才會產生）". Switching the track swaps the `<video>`'s MediaSource (`emptied`; a new main MediaSource at 8 of 8 switches on 4 videos, starting with init segments in the 2 inspected byte by byte) and resets its time to 0 until it seeks back: the page script posts its verdict at `emptied`, and the content script sends no chunk from `emptied` until that verdict arrives (at most 2 s; without it, 1 of 3 switches back to a dub still sent one chunk). Switching to the original makes captions start from the playhead; switching back stops new chunks (fake Groq, 4 videos: 0 requests in 8 dub phases).
- **Chunking**: request roughly 30–60 s ahead of the playhead (60 s of video at 1×; the lookahead scales with the playback rate, `forPlaybackRate`, up to 4×, because what keeps captions ahead is wall time; the "playhead is about to catch up" margin below is in wall seconds too); a short first chunk (10 s) after start/seek; cancel or deprioritise work that a seek made irrelevant. No fixed grid: each chunk is about 30 s from where the last one ended, and its end is only a target. The content script decodes up to 4 s past it and cuts at the quietest 0.3 s window up to 6 s earlier or 4 s later (`findQuietCut`, `src/content/energy.ts`); nothing after a chunk is scheduled until its cut is known. When the cut is not in a real pause (more than 6 dB above the chunk's quietest tenth), a last line that runs into the cut is dropped and the next chunk starts where it began (`trimCutSentence`). No request shorter than 8 s except the first chunk and when the playhead is about to catch up (Groq bills 10 s minimum): 8 s or more when the chunk starts within 6 wall s of the playhead, 3 s or more only when it starts within 2 s and the playhead is within 3 s of the end of the buffered audio (`sendWhatIsBuffered`); without the last condition a start that no longer waits for the next tick sent the first 4–6 s YouTube had appended (2 of 4 runs) and a second request right after.
- **Segmentation** (`src/background/segmentation.ts`): words are matched to segments by text position (their times overlap when people talk over each other), and each segment's words are grouped into lines; segment boundaries (often a change of speaker) always break, but a segment under 4 characters joins its neighbour. Lines break at sentence ends and pauses over 0.7 s; longer runs are split into balanced lines at the cheapest break (`breakPenalty`: Whisper's phrase gaps, commas and particles are cheap; inside kanji, katakana or a number with its unit is nearly forbidden). Fragments under 4 characters are joined to a neighbour, lines that would show under 0.8 s are joined to the next (rapid dialogue), a stretched first or last word does not stretch the line. Max 24 characters (Japanese), 32 (Korean), 7 s.
- **Whisper's prompt** (`buildWhisperPrompt`, `src/shared/video-context.ts`): the most recent captions only: the last 4 lines that ended in the 30 s before the chunk (`recentLines` in the content script; 11–110 characters, median 59, in the 276 non-empty prompts of the 48 current captures, so the 200-estimated-token cap, Whisper reads at most 224 and keeps the last ones, `estimateWhisperTokens` counting 1.5 per kana, kanji or Hangul syllable and ⅓ per ASCII character, is never reached). Never the video's title, channel, description or tags: with them at the front (PR #9), Whisper decoded garbage on some videos ("テレレレレレレレ.", "衆印印印印…", avg_logprob < −1) that the filters dropped, so almost no captions appeared (A/B on the same original audio, 180 s each: cth3M1iavGM 79 vs 774 characters, dZgXCAWnz2c 17 vs 997), and they spelled names no better (2/5 → 2/5 on wGri81E7g_E); with the tags in the prompt, Whisper also put names from them in as speaker labels (ByUh5ZUTMw4: 「岩本」「スノ」 in every line). Groq's Whisper repeats itself at temperature 0 (the same WAV and prompt gave the same words in 22 of 24 chunks, 44 of 44 repeats; the 2 others were fallback windows, which sample), so a difference between two captures of the same audio is the prompt (or the chunk cuts), and a prompt change moves single chunks both ways: after PR #13 Whisper wrote 4.6% fewer characters on the re-recorded windows and QXzN05rrY4E lost two interview quotes, but a longer prompt (the last 90 s of captions up to the 200-token cap) changed 29 chunks not picked by the result by a median of 2.3%, 11 up and 10 down (characters 3,656 → 3,652; C coverage 60% → 62%, CER 0.461 → 0.467), and no prompt was no better, so the prompt stays as it is (the `test-extension-in-browser` skill, section 8, "Replaying the same audio"). The video info is for the translator: the page script reads `videoDetails` (title, author, shortDescription, keywords) from the player responses it accepts for patching (not the made-up ones; see "Where captions appear") and posts it as `video-info`, again every few seconds for the current video; the translation prompt gets the title and channel (see "Translation requests").
- **Made-up text over music/silence** (`rejectReason`, `repetitiveFallbacks` in `src/background/segmentation.ts`): segments are dropped when Whisper aligned no word to them; when they are the fourth identical segment in a row (people greet each other or say いただきます together up to three times: 3 of 3 such runs on the evaluation set were real) or repeat (10+ characters) the prompt; when they are only a bracketed note ("〈字幕〉", "[音楽]") or a known phrase (Korean subtitle credits, "자막 제공 배달의민족", "한글자막 by 한효정"; a whole segment that is a news sign-off, 「MBC 뉴스 김성현입니다」, which Whisper wrote over a Korean vlog with a TV drama in the background (kxVk735LST8: made up or heard from the TV, not checked); real reports in the set sign off with KBS or SBS, and lose only that line if MBC); when Whisper counts them as probably no speech and is not sure of the text (`no_speech_prob > 0.4` and `avg_logprob < -0.3`: 3 of 2,301 segments score over 0.4, two made-up outros over intro music at -0.51 and -0.34 and one real line at -0.15); when the decoder failed (`avg_logprob < -1`); and in a fallback-temperature window (Whisper failed at temperature 0 and decoded again hotter) whose text repeats itself (fewer than 75% distinct character pairs): all of it when it is unsure (`avg_logprob < -0.8`), else the segments whose text recurs in another segment of the window or that share at least 40% of their three-character sequences with one, and the whole window when at least 3 in 4 of its segments loop. Decode statistics are shared by all segments of a 30 s window, so a per-window rule must not throw away real speech in it: the old loop rule (any one shared sequence) dropped 9 lines of real talk in one window of LKTOWTc9l1E (183 characters score under 75% distinct pairs from ordinary words alone), and the unsure-fallback rule, applied to any fallback window (PR #17), dropped 6 lines of real talk in the only unsure fallback window with the current prompt (nOSYk1M9KBo 139 s, temperature 0.4, -0.91). The whole-window share separates the two looping windows of the set: an ingredient list over BGM (LHZgl2pbY7Q 110 s, temperature 0.2, avg_logprob -0.25, 「クリームチーズ」「マヨネーズ」「塩」「コショウ」「オイル」…, 12 of 15 segments loop) and a couple saying おいしい over breakfast (5Ma5inm_Dac 304 s, 7 of 11, the other 4 kept). Over all 48 videos with the current prompt (the `test-extension-in-browser` skill, section 8): 2 of 2,137 shown segments are made up (before PR #21: 12 of 2,138) and 4 of 2,139 speech segments are dropped (before: 13); the 2 shown are single lines in windows of real talk that no creator line covers (bQ1-VvITMvY 「봐봐」, _xhw8bUhWOk 「상민아 왜 그래.」), the 4 dropped are 「...」, a failed decode (-1.66), a line Whisper copied from the prompt into 0.5 s at a chunk's end, and a fourth 「안녕하세요」. Tried and not used (2026-11-09): the voiced-frame share of a segment's own span (music scores as voiced: the ingredient segments 0–100%), `compression_ratio` (the ingredient window 2.08, a window of real talk in ByUh5ZUTMw4 2.03), characters per second of a window (real talk windows go down to 0.9), the share of 20 ms words; Groq's verbose_json has no word probabilities. kxVk735LST8 is not a no-speech control: its creator does not talk, but a Korean TV drama plays in the background (the user listened), so its segments are unsure (until 2026-11-09 it counted as no speech: "9 of 73 made-up segments shown" on it and LHZgl2pbY7Q). Judge filter changes only on captures made with the current Whisper prompt: with the title in the prompt (PR #9, fixed in #13) Whisper made up different text.
- **Rate limiting**: every Groq request goes through one limiter in the background (`src/background/rate-limiter.ts`), with our own ceilings a little under the free tier: Whisper 18 req/min and 7,000 audio s/hour (each request billed as at least 10 s, as Groq does); gpt-oss 28 req/min and 7,500 tokens/min. It also obeys Groq's `x-ratelimit-remaining-*` / `x-ratelimit-reset-*` headers (Groq sends `requests` (per day), `tokens`, `audio-seconds`) and a 429's `retry-after`, and its log survives service worker restarts in `chrome.storage.session`. A translation is recorded with an estimate (`estimateChatTokens`: about 4 ASCII characters per token, 1 per kana, kanji or Hangul, plus 40 per line and 400) and corrected with `usage.total_tokens` when the reply comes; a 429 or 5xx frees its estimate (nothing billed), and a waiting request re-checks at least every second (`RECHECK_MS`), so a corrected estimate lets it go at once. Before (2026-11-09, qpNlAXE004Y with fake Groq: 11–12 lines per 30 s chunk, 1,500 tokens per reply, 180 s at 1×), the English system prompt counted as 1.1 tokens per character made every estimate about 1,700 tokens too big and a waiting request slept until the oldest estimate left the minute: translations waited 23–32 s, one 64 s after a failure's estimate, and the playhead passed chunks still in Japanese.
- **Quota and usage** (`src/shared/quota.ts`): the background records what Groq billed (Whisper: requests and audio seconds, at least 10 s each; translation: requests and `usage.total_tokens`) per hour and per video (`videoId` in the request) in `chrome.storage.local` `groqUsage`. Today's budget: daily requests from Groq's `x-ratelimit-*-requests` headers while fresh (limit from `x-ratelimit-limit-*`); tokens and audio seconds estimated as the free-tier daily limit minus our last 24 hours (the headers only report shorter windows), scaled up when Groq reports a higher daily request limit (a paid plan). Under 10% of any daily budget: translation is paused (the background answers `quotaPaused` without calling Groq; captions stay in the original, uncached); Whisper low → one chunk at a time and 30 s lookahead; Whisper out → nothing is scheduled (checked again right before a chunk is sent) and the status line says so, ahead of any other error (not for creator captions, which need no Whisper); the content script schedules nothing until its first `get-quota` reply. The popup shows the budgets, the warnings and the current video's usage.
- **Translation requests**: `reasoning_effort: "low"`, JSON mode, lines sent and returned as a numbered object (`{"1": …, "2": …}`). A plain list let the model merge a sentence split over two lines and shift every later translation by one; telling the model to "spread one sentence over the lines" brought the shift back (Korean variety, 14 of 21 lines), so the prompt insists that every key translates only its own line. The prompt also asks to infer what was said when speech recognition is wrong, to translate idioms by meaning, to drop pure fillers, Taiwanese vocabulary for zh-TW, and established names. Context is the previous lines as `original → translation`, after the video's title and channel. **Glossary** (`src/shared/glossary.ts`): the reply also has `"terms"` (names of people, groups, shows, places and recurring terms in the lines → how they were translated); the content script keeps the first rendering of each term per video (only terms that occur in the lines; at most 60), sends the entries whose term occurs in the lines or context (at most 20) as "renderings already used in this video", replaces another rendering of a known term in a reply (two chunks translated at once) with the established one (`applyGlossary`), and keeps the glossary across seeks and in the cache entry; changing a caption-shaping setting starts a new one. A chunk waits (at most 5 s) for the chunk before it, so the Whisper prompt and translation context are not empty during the start-up burst. **A failed translation is sent once more** (2 s later) when it may pass: Groq's 5xx or 429 after the limiter's retries, a reply that is not readable JSON or Groq's `json_validate_failed` 400, a network error (`isRetryable`); not a bad key or a rejected request. Lines a reply leaves out (`missing`) are asked for alone in one more request instead. So at most one extra request per chunk; after that the chunk shows the original (not cached). Before, one failure left the whole chunk (11–12 lines in a talk show) in the original for the rest of the visit: with every third translation failing (fake Groq, qpNlAXE004Y, 180 s at 1×), 34 of 67 lines were never translated; after, 1 of 67 (the first line, shown before the first reply), at 13 translation requests instead of 8 (the dense run without failures: 4 → 2 lines ever shown untranslated, 2 → 1 never translated).
- **Start-up**: the content script ticks every second, and also at once when something the start waits for arrives (a video's first audio, the page script's creator-track answer, the cache, the first quota reply), and asks for the quota while the source is still being decided, so these steps do not each wait for the next tick. Measured with fake Groq replying in 0.9 s (2026-11-09): the source was decided 1.4–1.6 s after the first audio before (W1iGWTlt_hU 2 runs, bEkRwcZrJsg 1) and 0.0–0.3 s after (6 runs on the same two); the first caption on W1iGWTlt_hU 7.4–8.3 s after the page script loaded before, 4.8–5.6 s after (2 runs each with the final build).
- **Voice activity**: before Whisper, the content script computes spectral features per 20 ms (`src/content/voice.ts`) and skips a chunk when no 3 s window has at least 45% voiced frames. A frame is voiced when its 300–3400 Hz flatness is ≤ 30% and either 300–3400 Hz holds ≥ 45% of the energy, or the frame is audible (300–3400 Hz level ≥ −60 dB) and that level spans ≥ 15 dB within ±0.24 s (syllables switching on and off), whatever else the spectrum holds. The syllable rule replaced a low-voice rule (150–3400 Hz ≥ 70% and a 24 dB swing): a low voice keeps most of its energy at its fundamental (cth3M1iavGM: median 35% in 300–3400 Hz while speaking), and talk over music or with a breathy voice failed both old rules. It leans towards sending (agreed with the user: recall first; the filters after Whisper catch what music lets through, "Made-up text"), but not all the way: dropping the flatness condition and lowering the threshold to 30% skipped only 9 of 1,111 no-speech 30 s chunks (1 of 6,479 lines lost in 10 s chunks), and the filters still let 9 of 73 made-up segments through on the no-speech captures made with the current prompt (both counts with kxVk735LST8, see below, still taken as no speech). Tuned on the evaluation set (`node scripts/qa-eval.ts`, 48 videos, chunks of 10 and 30 s starting every second, creator tracks as labels): lines that ever fell in a skipped chunk 27 of 6,479 for 10 s chunks (before: 278) and 0 for 30 s (before: 15); cth3M1iavGM 2 and 0 of 154 (before: 41 and 9); reality shows 16 and 0 of 1,580 (before: 135 and 6); no category lost recall. The price: no-speech 30 s chunks skipped 0 of 597 (the old rule not rerun on these): voice detection sends nearly all BGM, and the two silent mitsuba vlogs were sent almost entirely before and after. kxVk735LST8 (its creator does not talk, but a Korean TV drama plays in the background while she eats; the user listened) is neither talk nor a no-speech control (`backgroundSpeech` in `src/qa/dataset.ts`): the 125 of 1,111 no-speech 30 s chunks skipped there by the syllable rule (315 before), once read as "skipping silence", are unsure, and its old "17% talk recall" was never the creator's voice. Silence (a track without sound, −100 dB) still scores 0. A playhead in a finished chunk with no caption shows "這段沒有辨識到台詞" rather than "等待音訊…".
- **Playback edge cases** (measured on 2026-11-08 in agent-browser, `CMr1oFunZpA` (1:23:52, Japanese talk), translation off; leads are "seconds of finished chunks contiguous from the playhead", `lead` in the content script's `state` log line):
  - **Speed**: at 2× the old 60 s lookahead gave a lead of 55–80 video s (median 66, about 33 wall s; 1 run, 11 samples after start-up); with the lookahead scaled to 120 s it is 88–118 (median about 100, 50 wall s; 2 runs) and is then bounded by YouTube's own audio buffer (about 120–130 s ahead of the playhead at 2×; the `reason` then says "音訊還沒涵蓋…"). 1.5×: 89–110 (60–73 wall s); 1×: 60–80. Whisper stayed at 4.4 (1×) to 5.9 (2×) requests/min (limit 18) with about 1 s latency. What does not scale: audio seconds. At 2× with speech throughout, Whisper bills about 160 audio s per wall minute, so the hourly 7,200 s ceiling is reached after about 45 minutes of 2× viewing (then the limiter makes chunks wait and captions fall behind) and the daily 28,800 s after about 3 hours. A speed change mid-video applies on the next tick (the schedule is recomputed every second). After a mid-roll ad YouTube appends the audio again under a new init segment, so the lead restarts from where the playhead is.
  - **Long videos**: the audio store keeps finished audio for 120 s behind the playhead and drops any audio more than 600 s away (`MAX_DISTANCE_SECONDS`), pruned on every tick except during an ad (the `<video>` then plays the ad from 0). Before, it was pruned only after a chunk was scheduled, so with the extension on but nothing sent (no key, Whisper out, a range that kept failing) every byte stayed: 13.9 MB after 1,210 s of video (about 11.5 KB/s, so about 80 MB for two hours); now it levels off at 8.4 MB (600 s behind plus YouTube's buffer ahead), the same at 1,870 s. Linear playback with chunks being sent held about 3 MB either way. Cues and jobs are small (548 cues for 1,540 s). The cache entry grows with the video: 37.7 KB of JSON for 1,540 s transcribed (about 25 characters per second), so a fully watched 2-hour video is about 180 KB without translation and more with it; tens of those fill `chrome.storage.local`.
  - **Live streams**: no captions. The page script records `videoDetails.isLive` from every player response (`liveStatus`; a later response for the same video without it, its recording, clears it), adds no track to it and tells the content script (`live` in `caption-mode`); the content script then keeps none of its audio and schedules nothing, the popup says "這支影片不產生字幕（直播不支援）", and no status shows on the player. `video.duration` is finite on a live stream (50,396 s on one), so it cannot tell. Before, the live MP4 audio (a new init segment with each fragment) never added up to a chunk, so nothing was sent, but its audio piled up (about 17 KB/s) without ever being pruned.
  - **Shorts** (`/shorts/…`): no captions, for the same reasons and with the same popup note. They play in `#shorts-player`; a hidden `#movie_player` stays from an earlier watch page, and before this the content script read that one's time (always 0) and transcribed the first minute of a Short whatever was playing.
  - **Music videos**: captioned like speech, on purpose. Singing counts as voice: on YOASOBI's "アイドル" MV (`ZRtdQ81jPUQ`, 3:46) 8 of 9 chunks scored 45–89% voiced and only the instrumental outro was skipped (measured before the syllable rule, which sends more); Whisper's lines were the lyrics with a few mishearings, not made-up text (read by hand, 1 video), at 7 requests and 189 s of audio. Lyrics are what a viewer of a Japanese or Korean MV wants translated, so there is no music-video rule.
  - **Videos without sound**: an upload without sound still carries a (silent) audio track (1 of 1 checked, `RhpCA7ncmRY`); every chunk scored 0% voiced (8 of 8), so nothing is sent; like any finished chunk without a caption it gets the status "這段沒有辨識到台詞".
  - **Translation at 2×**: the binding limit is tokens per minute, not requests. A chunk's translation costs about 800–1,650 tokens (prompt with context and glossary), so 2× (about 4 chunks a minute) needs about 6,000 of our 7,500 tokens/min, and the start-up burst (the playhead plus the lookahead, 9 chunks in the first 80 s of one run) needs more: the limiter held two translations until the playhead passed them, so they were cancelled and those 57 s showed the original only (1 run, 8,243 tokens for 6 translations). Whisper itself kept ahead. Other threads or tabs sharing the key make it worse (Groq's own limit is 8K tokens/min per key).
- **Caption data**: `Cue` (`src/shared/captions.ts`, seconds, `original` + optional `translation`) converts one-to-one to YouTube timedtext json3 (`toJson3`); the CC-menu track shows the translation, with the original on the line above when "翻譯上方顯示原文" is on. The content script bumps a version on every change to a video's cues (`setCues`, or `cuesVersion++` after editing a cue in place) and resends the track only when the version or the text settings changed; never compare the serialized cues on a timer.
- **Cache**: finished chunks per video and per caption-shaping settings in `chrome.storage.local` (`cache:<video>:<whisper model>:<language>:<translation or none>`, or `creator:<language>` in place of the model and language for a creator track's lines), at most 50 entries and 30 days. Several tabs save at once, so there is no shared index: each entry has its own `cachemeta:<…>` key (its `savedAt`), set and removed in the same storage call as the entry; eviction lists the meta keys (`getKeys()`), and an entry without one (older versions kept a shared `cacheIndex`, which lost updates) gets it rebuilt from its own `savedAt`; before removing, eviction re-reads the candidates' meta keys and keeps any another tab just saved again; a failed write (storage full: `chrome.storage.local` holds 10 MB and a long video's entry is large, see "Playback edge cases") evicts the oldest other entries, one and then twice as many each time, until it fits, so it recovers however few entries there are; without `getKeys()` (Chrome < 130) keys are listed with `get(null)`. Chunks whose translation failed are not cached. The entry also holds the video's translation glossary.

## Stack

- React + Vite + shadcn/ui + Tailwind CSS for the popup/options UI.
- No Radix Select in the action popup: it locks the page's scroll while open, which removes the popup's scrollbar and resizes the popup window (335 → 350 px wide), and it closes itself on any window `resize` or `blur`, so it shut again within 0.2 s (in a real action popup: 4 of 4 selects with the mouse at the top and bottom, 4 of 4 with the keyboard in the middle; with its `resize` listener suppressed, 4 of 4 stayed open). Other Radix parts that lock scroll (a modal DropdownMenu, Dialog) are untested there; check them in the real popup before using them. Choices use a native `<select>` styled like shadcn (`src/components/ui/native-select.tsx`). A popup opened as a tab (`chrome-extension://<id>/popup.html`) does not resize and hides the bug; test the popup with `chrome.action.openPopup()` (the `test-extension-in-browser` skill, section 3).
- TypeScript 7 (`tsc` v7, the native compiler) for type checking.
- oxlint for linting, oxfmt for formatting. No ESLint or Prettier.
- pnpm (via corepack) as the package manager.
- Content script (isolated world), page script (MAIN world) and service worker are separate entry points.
- Build: plain Vite 8, one build per entry point, driven by `scripts/build.ts` (no `@crxjs/vite-plugin`). The page script must run synchronously at `document_start`, before YouTube's player code, so it is bundled as a single classic script (IIFE) with no loader; CRXJS injects content scripts through an async dynamic-import loader, which would install the `appendBuffer` hook too late. The content script is an IIFE too (content scripts cannot be ES modules); the service worker is an ES module; the popup is a normal Vite HTML build (`vite.config.ts`).
- `public/manifest.json` is copied to `dist/` as is; edit it there. `vite build` alone builds only the popup: use `pnpm build`.

## Project layout

- `src/page/` MAIN-world page script (hooks the audio, posts it with `window.postMessage`; serves the CC-menu caption track).
- `src/content/` isolated-world content script (chunking, scheduling, captions).
- `src/background/` service worker (speech-to-text and translation API calls).
- `src/popup/` settings popup (React); `src/components/ui/` shadcn/ui components (add more with `pnpm dlx shadcn@<version> add <name>`, then check that imports use `@/lib/utils`).
- `src/shared/` code shared by the entry points: message types (`messages.ts`), settings and `chrome.storage.local` access (`settings.ts`), caption data (`captions.ts`), YouTube URL helpers (`youtube.ts`), the `[yt-ai-subs]` log prefix (`log.ts`).
- Pure logic lives in its own module with a `*.test.ts` next to it (Vitest, Node environment, no `chrome.*`): WebM parsing, audio coverage, scheduling, segmentation, rate limiting, cache eviction, loudness and quiet cuts (`energy.ts`).
- `src/qa/` offline caption-quality evaluation (see the `test-extension-in-browser` skill): `timing-eval.ts` (run by `scripts/qa-replay.ts` on debug captures) and the **evaluation set**: `dataset.ts` (48 video IDs with spoken language, content type and voice type), `ground-truth.ts` (creator caption tracks as ground truth, filtered by the trap rules of the `research-youtube-captions` skill), `voice-eval.ts` (layer A: voice detection on simulated chunks starting every second), `caption-eval.ts` (layer B: each Whisper segment kept or dropped against speech; layer C: coverage, CER, line timing, translation chrF), `audio-track.ts` (refuses captures of YouTube's AI-dubbed audio), `fixture.ts` (CI fixtures), all run by `scripts/qa-eval.ts`. Debug captures and caption tracks hold other people's text: they live in `.qa/` (gitignored) or a scratchpad, never in git; only voice features and speech intervals without text are committed (`src/test/eval/`). Keep browser glue (`index.ts`, `wav.ts`'s decoding, `overlay.ts`) thin. Test fixtures go in `src/test/`.
- `.claude/skills/test-extension-in-browser/eval-collect.py`, `eval-plan.py`: host-side collection of the evaluation set with agent-browser (creator tracks, dry runs, Whisper runs within a request budget). They set the development-only settings `debugCapture`, `debugDryRun` and `debugForceWhisper` (Whisper even for videos with a usable creator track, which every video of the set has). `chunk-replay.py` sends the same chunk audio to Whisper again (recorded with fake Groq replies, checked against the captures' loudness envelopes), to compare prompts or models on identical input.
- `test/ad-skip/` a test-only MV3 extension (plain JS, no build) that mutes, fast-forwards and skips YouTube ads, loaded next to `dist/` in every agent-browser run so ads do not eat test time (the player sends no timedtext requests during an ad). Not part of the product: it is outside `public/`, `pnpm build` never copies it, and the release zip holds only `dist/`.
- `test/fake-groq/` a test-only CDP client (`node`, run on the VM next to agent-browser; it listens on nothing) that answers the service worker's Groq requests with fake replies and chosen `x-ratelimit-*` budgets, to drive the quota levels and the rest of the background without calling Groq (the `test-extension-in-browser` skill).

## Scripts

Run them in the dev container (see the next section).

- `pnpm build` builds the unpacked extension into `dist/` (production, minified).
- `pnpm dev` rebuilds `dist/` on change (development, inline source maps). Reload the extension in `chrome://extensions` (and the YouTube tab) after a rebuild. Changes to `public/manifest.json` need a restart of `pnpm dev`.
- `pnpm typecheck` (`tsc -b`), `pnpm lint` (oxlint), `pnpm format` / `pnpm format:check` (oxfmt).
- `pnpm test` runs the unit tests (Vitest, `vitest.config.ts`).
- `pnpm check` runs typecheck, lint, format:check and test; it must pass before a commit. The tests include `src/qa/fixture.test.ts`: voice detection on committed stretches of the evaluation set (a low male voice, a high female voice, talk over BGM, BGM only) must not lose talk or let more music through than when the floors were set.
- `node scripts/qa-eval.ts` scores the captions on the evaluation set from `.qa/` (no API calls): a table per video and per content type, voice type and language for layers A, B and C; `--dataset` shows what each video's ground truth supports, `--video <id>` every number of one video, `--write-fixture` writes a CI fixture. Collecting `.qa/` takes agent-browser on the host and, for Whisper runs, Groq (the `test-extension-in-browser` skill, section 8).

## Development workflow

Every change goes through these five steps, in order:

1. **Plan** with the `plan-it` skill: approach, scope and how it will be verified.
2. **Implement** with the `implement-plan` skill, until `pnpm check` and `pnpm build` pass.
3. **Review** the diff with the `review-change` skill (`git diff main...HEAD` plus uncommitted changes). The review is done by Codex `gpt-6.1-sol` at medium reasoning effort, delegated from the working thread in the same worktree (the reviewers `review-change` spawns run as t3 `delegate_task` children with `role: "review"`, `isolation: "shared"`, `target.model: "gpt-6.1-sol"` and medium reasoning effort; settle them once they report); it reports findings only and does not edit files. Fix what it finds; re-run the review only after large changes.
4. **Verify** in a real browser: install the built extension with agent-browser and check the effect on a YouTube page (the `test-extension-in-browser` skill; keep evidence with the `verification-evidence` skill).
5. **Merge through a pull request**: push the branch and open a PR with `gh pr create --base main` (the body says what changed and how it was verified, and ends with `🤖 Generated with [Claude Code](https://claude.com/claude-code)`). When the CI workflow (`.github/workflows/ci.yml`: `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm build`) passes, merge with `gh pr merge --merge --delete-branch`; if it fails, fix and push to the same PR. Never push to `main` directly. t3 settles the thread once the PR is merged. Step by step: the `ship-pr` skill. Publishing a downloadable version: the `release-extension` skill.
