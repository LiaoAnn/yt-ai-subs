# yt-ai-subs

Chrome extension (Manifest V3) that transcribes YouTube audio with a speech-to-text model and, optionally, translates it with an LLM, a few chunks ahead of the playhead, so it only spends money on what the viewer actually watches.

## How agents keep knowledge

- Do not use agent memory features (Claude memory, Codex memories, etc.). Anything worth remembering goes into the repo:
  - project decisions and conventions → this file;
  - repeatable procedures (testing in the browser, releasing, debugging the audio hook) → a skill under `.claude/skills/<name>/SKILL.md`;
  - rules that can be checked mechanically → a lint rule or a test, not prose.
- When a decision here changes, update this file in the same change.
- Work is split across t3 threads: a supervisor hands tasks out with the `delegate-to-thread` skill, and a delegated thread works and reports with `run-delegated-task`. A brief that keeps repeating the same instructions means they belong in a skill.

## Product decisions

- **Provider**: Groq first (Whisper `whisper-large-v3` / `whisper-large-v3-turbo` for speech-to-text, `openai/gpt-oss-120b` / `openai/gpt-oss-20b` for translation). OpenRouter / OpenAI are optional extras for translation. No xAI/Grok, no Codex subscription.
- **Groq free tier limits** (design the scheduler to stay under them):
  - Whisper: 20 requests/min, 2,000/day, 7,200 s audio/hour, 28,800 s audio/day, 25 MB per file.
  - gpt-oss-120b / 20b: 30 requests/min, 1,000/day, 8K tokens/min, 200K tokens/day.
- **Languages**: mainly Japanese and Korean sources, Traditional Chinese (Taiwan) target. Translation is optional: a transcribe-only mode must work on its own.
- **Where captions appear**: in YouTube's own caption (CC) menu as a selectable track ("AI 繁中", "AI 英文" or "AI 原文", named from the settings when the video loads; the player cannot rename it live: its track list is built once per video and neither its player response, a captions reload, reloading the captions module nor `updateVideoData` renames it (the last pauses playback), so the popup notes that a renaming save applies from the next video or reload), drawn by YouTube's renderer with the viewer's caption settings. The page script adds the track to every player response (`ytInitialPlayerResponse`, `/youtubei/v1/get_watch` and `/player` via `fetch`), answers the player's timedtext XHR for it with our json3, selects it once per video, and reloads it when new cues arrive. The overlay is only the fallback, used per video when a health check sees the hook break; the popup shows which mode the tab uses. How it works and how to debug it: the `debug-caption-track` skill.
- **Creator captions first** (`src/shared/creator-captions.ts`, `src/page/creator-hooks.ts`, `src/content/creator-source.ts`): the page script notes each player response's caption tracks before adding ours. (1) A creator-uploaded track (no `kind`) already in our track's language (zh-TW target: `zh-Hant*`, `zh-TW`, `zh-HK`, `zh-MO`; plain `zh` is ambiguous and does not count) while translating: our track is not added, the page script selects the creator's track once per video (the viewer can still switch), nothing is transcribed or translated, and the popup says "創作者上傳的字幕". Selecting beats a note: the viewer installed the extension to get these captions without doing anything, and a human translation costs nothing. (2) A creator track in the spoken language (the setting, or the automatic track's language for "auto"): it and YouTube's automatic track of that language are fetched, and if usable its lines replace Whisper's and are only translated, in 60 s chunks up to 120 s ahead (cache key `cache:<video>:creator:<language>:<translation>`; with translation off, nothing is called at all). Not usable, so Whisper as before: a copy of the automatic track (error rate under 0.1 and p90 of the line-start difference ≤ 0.1 s; hand-made text with YouTube-aligned timing has offset 0 but about 0.2 error rate, so both are required), a track covering under half of the automatic track's lines (summary cards), an empty or unfetchable track. Fetching needs the player's `pot` token: the player adds it only to URLs that look like a real track's, so our track's baseUrl copies a real track's parameters, and the token from the player's request for our track fetches any track of the video. The content script schedules nothing until the page script has answered (at most 15 s ad-free without an answer, 30 s while fetching). Like the track name, the choice is made once per video from the settings at load (the player cannot change its track list live); a settings save that renames the track says so in the popup. Translation prompts get a rule for caption cards (`[…]`, `(…)`, `【…】`) and speaker labels (`name / …`, `name：…`) only when a line has one.
- **Audio source**: copy the audio YouTube already appends to its MediaSource buffers (hook `SourceBuffer.prototype.appendBuffer` in the page's MAIN world). Never download media from googlevideo directly. Appends do not follow WebM element boundaries: `AudioStore` (`src/content/audio-store.ts`) searches for cluster headers in the last 40 bytes of the previous append plus the new one, so a header split across appends still starts its own cluster; an append that itself starts with a whole cluster header (a seek) is never joined to the previous tail.
- **Chunking**: request roughly 30–60 s ahead of the playhead (60 s of video at 1×; the lookahead scales with the playback rate, `forPlaybackRate`, up to 4×, because what keeps captions ahead is wall time; the "playhead is about to catch up" margin below is in wall seconds too); a short first chunk (10 s) after start/seek; cancel or deprioritise work that a seek made irrelevant. No fixed grid: each chunk is about 30 s from where the last one ended, and its end is only a target. The content script decodes up to 4 s past it and cuts at the quietest 0.3 s window up to 6 s earlier or 4 s later (`findQuietCut`, `src/content/energy.ts`); nothing after a chunk is scheduled until its cut is known. When the cut is not in a real pause (more than 6 dB above the chunk's quietest tenth), a last line that runs into the cut is dropped and the next chunk starts where it began (`trimCutSentence`). No request shorter than 8 s except the first chunk and when the playhead is about to catch up (Groq bills 10 s minimum).
- **Segmentation** (`src/background/segmentation.ts`): words are matched to segments by text position (their times overlap when people talk over each other), and each segment's words are grouped into lines; segment boundaries (often a change of speaker) always break, but a segment under 4 characters joins its neighbour. Lines break at sentence ends and pauses over 0.7 s; longer runs are split into balanced lines at the cheapest break (`breakPenalty`: Whisper's phrase gaps, commas and particles are cheap; inside kanji, katakana or a number with its unit is nearly forbidden). Fragments under 4 characters are joined to a neighbour, lines that would show under 0.8 s are joined to the next (rapid dialogue), a stretched first or last word does not stretch the line. Max 24 characters (Japanese), 32 (Korean), 7 s.
- **Whisper's prompt** (`buildWhisperPrompt`, `src/shared/video-context.ts`): the video's title (without hashtags, emoji and ASCII tags like `[ENG SUB]`), channel, and names from the description and tags (people on a cast line such as `출연:` / `出演` / `ゲスト`, hashtags, then tags written in the source language's script; terms already in the title or channel are left out), then the most recent captions. Whisper reads at most 224 tokens and keeps the last ones, so the video part goes first and is capped at about 80 estimated tokens, the whole prompt at 200 (`estimateWhisperTokens` counts 1.5 per kana, kanji or Hangul syllable, ⅓ per ASCII character). The page script reads `videoDetails` (title, author, shortDescription, keywords) from every player response it already patches and posts it as `video-info`, again every few seconds for the current video.
- **Made-up text over music/silence**: segments are dropped when Whisper aligned no word to them, when they repeat the segment before or (10+ characters) the prompt (title and terms included), when the decoder failed (`avg_logprob < -1`), and when a fallback-temperature window loops on itself (fewer than 75% distinct character pairs). Decode statistics are shared by all segments of a 30 s window, so a per-window rule must not throw away real speech in it.
- **Rate limiting**: every Groq request goes through one limiter in the background (`src/background/rate-limiter.ts`), with our own ceilings a little under the free tier: Whisper 18 req/min and 7,000 audio s/hour (each request billed as at least 10 s, as Groq does); gpt-oss 28 req/min and 7,500 tokens/min. It also obeys Groq's `x-ratelimit-remaining-*` / `x-ratelimit-reset-*` headers (Groq sends `requests` (per day), `tokens`, `audio-seconds`) and a 429's `retry-after`, and its log survives service worker restarts in `chrome.storage.session`.
- **Quota and usage** (`src/shared/quota.ts`): the background records what Groq billed (Whisper: requests and audio seconds, at least 10 s each; translation: requests and `usage.total_tokens`) per hour and per video (`videoId` in the request) in `chrome.storage.local` `groqUsage`. Today's budget: daily requests from Groq's `x-ratelimit-*-requests` headers while fresh (limit from `x-ratelimit-limit-*`); tokens and audio seconds estimated as the free-tier daily limit minus our last 24 hours (the headers only report shorter windows), scaled up when Groq reports a higher daily request limit (a paid plan). Under 10% of any daily budget: translation is paused (the background answers `quotaPaused` without calling Groq; captions stay in the original, uncached); Whisper low → one chunk at a time and 30 s lookahead; Whisper out → nothing is scheduled (checked again right before a chunk is sent) and the status line says so, ahead of any other error (not for creator captions, which need no Whisper); the content script schedules nothing until its first `get-quota` reply. The popup shows the budgets, the warnings and the current video's usage.
- **Translation requests**: `reasoning_effort: "low"`, JSON mode, lines sent and returned as a numbered object (`{"1": …, "2": …}`). A plain list let the model merge a sentence split over two lines and shift every later translation by one; telling the model to "spread one sentence over the lines" brought the shift back (Korean variety, 14 of 21 lines), so the prompt insists that every key translates only its own line. The prompt also asks to infer what was said when speech recognition is wrong, to translate idioms by meaning, to drop pure fillers, Taiwanese vocabulary for zh-TW, and established names. Context is the previous lines as `original → translation`, after the video's title and channel. **Glossary** (`src/shared/glossary.ts`): the reply also has `"terms"` (names of people, groups, shows, places and recurring terms in the lines → how they were translated); the content script keeps the first rendering of each term per video (only terms that occur in the lines; at most 60), sends the entries whose term occurs in the lines or context (at most 20) as "renderings already used in this video", replaces another rendering of a known term in a reply (two chunks translated at once) with the established one (`applyGlossary`), and keeps the glossary across seeks and in the cache entry; changing a caption-shaping setting starts a new one. A chunk waits (at most 5 s) for the chunk before it, so the Whisper prompt and translation context are not empty during the start-up burst.
- **Voice activity**: before Whisper, the content script computes spectral features per 20 ms (`src/content/voice.ts`) and skips a chunk when no 3 s window has at least 45% voiced frames. A frame is voiced when its 300–3400 Hz flatness is ≤ 30% and either 300–3400 Hz holds ≥ 45% of the energy, or (a low voice) 150–3400 Hz holds ≥ 70% and the 300–3400 Hz level spans ≥ 24 dB within ±0.24 s (syllables switching on and off). The low-voice rule exists because a low male voice keeps most of its energy at its 150–300 Hz fundamental: on cth3M1iavGM (audio high-passed at 150 Hz) speech frames had a median 36% in 300–3400 Hz, and chunks scored 0.27–0.55, so 0:40–1:10 was skipped depending on where the chunks fell. Music's bass sits below 150 Hz and it does not stop between syllables, so the BGM-only vlog's scores did not change. Tuned on dry-run captures of seven videos with Whisper's lines as labels, simulating chunks of 10 and 30 s starting every second: 0 of 47 lines of the low voice (before: 42) and 0 of 128 news lines (before: 6) ever fell in a skipped chunk; 12 of 184 variety/idol lines did (before: 18), all sparse interjections in 10 s chunks; the BGM-only vlog sent 7% of its chunks and none with a made-up line, the same as before. A playhead in a finished chunk with no caption shows "這段沒有辨識到台詞" rather than "等待音訊…".
- **Playback edge cases** (measured on 2026-11-08 in agent-browser, `CMr1oFunZpA` (1:23:52, Japanese talk), translation off; leads are "seconds of finished chunks contiguous from the playhead", `lead` in the content script's `state` log line):
  - **Speed**: at 2× the old 60 s lookahead gave a lead of 55–80 video s (median 66, about 33 wall s; 1 run, 11 samples after start-up); with the lookahead scaled to 120 s it is 88–118 (median about 100, 50 wall s; 2 runs) and is then bounded by YouTube's own audio buffer (about 120–130 s ahead of the playhead at 2×; the `reason` then says "音訊還沒涵蓋…"). 1.5×: 89–110 (60–73 wall s); 1×: 60–80. Whisper stayed at 4.4 (1×) to 5.9 (2×) requests/min (limit 18) with about 1 s latency. What does not scale: audio seconds. At 2× with speech throughout, Whisper bills about 160 audio s per wall minute, so the hourly 7,200 s ceiling is reached after about 45 minutes of 2× viewing (then the limiter makes chunks wait and captions fall behind) and the daily 28,800 s after about 3 hours. A speed change mid-video applies on the next tick (the schedule is recomputed every second). After a mid-roll ad YouTube appends the audio again under a new init segment, so the lead restarts from where the playhead is.
  - **Long videos**: the audio store keeps finished audio for 120 s behind the playhead and drops any audio more than 600 s away (`MAX_DISTANCE_SECONDS`), pruned on every tick except during an ad (the `<video>` then plays the ad from 0). Before, it was pruned only after a chunk was scheduled, so with the extension on but nothing sent (no key, Whisper out, a range that kept failing) every byte stayed: 13.9 MB after 1,210 s of video (about 11.5 KB/s, so about 80 MB for two hours); now it levels off at 8.4 MB (600 s behind plus YouTube's buffer ahead), the same at 1,870 s. Linear playback with chunks being sent held about 3 MB either way. Cues and jobs are small (548 cues for 1,540 s). The cache entry grows with the video: 37.7 KB of JSON for 1,540 s transcribed (about 25 characters per second), so a fully watched 2-hour video is about 180 KB without translation and more with it; tens of those fill `chrome.storage.local`.
  - **Live streams**: no captions. The page script records `videoDetails.isLive` from every player response (`liveStatus`; a later response for the same video without it, its recording, clears it), adds no track to it and tells the content script (`live` in `caption-mode`); the content script then keeps none of its audio and schedules nothing, the popup says "這支影片不產生字幕（直播不支援）", and no status shows on the player. `video.duration` is finite on a live stream (50,396 s on one), so it cannot tell. Before, the live MP4 audio (a new init segment with each fragment) never added up to a chunk, so nothing was sent, but its audio piled up (about 17 KB/s) without ever being pruned.
  - **Shorts** (`/shorts/…`): no captions, for the same reasons and with the same popup note. They play in `#shorts-player`; a hidden `#movie_player` stays from an earlier watch page, and before this the content script read that one's time (always 0) and transcribed the first minute of a Short whatever was playing.
  - **Music videos**: captioned like speech, on purpose. Singing counts as voice: on YOASOBI's "アイドル" MV (`ZRtdQ81jPUQ`, 3:46) 8 of 9 chunks scored 45–89% voiced and only the instrumental outro was skipped; Whisper's lines were the lyrics with a few mishearings, not made-up text (read by hand, 1 video), at 7 requests and 189 s of audio. Lyrics are what a viewer of a Japanese or Korean MV wants translated, so there is no music-video rule.
  - **Videos without sound**: an upload without sound still carries a (silent) audio track (1 of 1 checked, `RhpCA7ncmRY`); every chunk scores 0% voiced, nothing is sent, and the status says "這段沒有辨識到台詞".
  - **Translation at 2×**: the binding limit is tokens per minute, not requests. A chunk's translation costs about 800–1,650 tokens (prompt with context and glossary), so 2× (about 4 chunks a minute) needs about 6,000 of our 7,500 tokens/min, and the start-up burst (the playhead plus the lookahead, 9 chunks in the first 80 s of one run) needs more: the limiter held two translations until the playhead passed them, so they were cancelled and those 55 s showed the original only (1 run, 8,243 tokens for 6 translations). Whisper itself kept ahead. Other threads or tabs sharing the key make it worse (Groq's own limit is 8K tokens/min per key).
- **Caption data**: `Cue` (`src/shared/captions.ts`, seconds, `original` + optional `translation`) converts one-to-one to YouTube timedtext json3 (`toJson3`); the CC-menu track shows the translation, with the original on the line above when "翻譯上方顯示原文" is on. The content script bumps a version on every change to a video's cues (`setCues`, or `cuesVersion++` after editing a cue in place) and resends the track only when the version or the text settings changed; never compare the serialized cues on a timer.
- **Cache**: finished chunks per video and per caption-shaping settings in `chrome.storage.local` (`cache:<video>:<whisper model>:<language>:<translation or none>`, or `creator:<language>` in place of the model and language for a creator track's lines), at most 50 entries and 30 days. Several tabs save at once, so there is no shared index: each entry has its own `cachemeta:<…>` key (its `savedAt`), set and removed in the same storage call as the entry; eviction lists the meta keys (`getKeys()`), and an entry without one (older versions kept a shared `cacheIndex`, which lost updates) gets it rebuilt from its own `savedAt`; before removing, eviction re-reads the candidates' meta keys and keeps any another tab just saved again; a failed write (storage full: `chrome.storage.local` holds 10 MB and a long video's entry is large, see "Playback edge cases") evicts the oldest other entries, one and then twice as many each time, until it fits, so it recovers however few entries there are; without `getKeys()` (Chrome < 130) keys are listed with `get(null)`. Chunks whose translation failed are not cached. The entry also holds the video's translation glossary.

## Stack

- React + Vite + shadcn/ui + Tailwind CSS for the popup/options UI.
- TypeScript 7 (`tsc` v7, the native compiler) for type checking.
- oxlint for linting, oxfmt for formatting. No ESLint or Prettier.
- pnpm (via corepack) as the package manager.
- Content script (isolated world), page script (MAIN world) and service worker are separate entry points.
- Build: plain Vite 8, one build per entry point, driven by `scripts/build.ts` (no `@crxjs/vite-plugin`). The page script must run synchronously at `document_start`, before YouTube's player code, so it is bundled as a single classic script (IIFE) with no loader; CRXJS injects content scripts through an async dynamic-import loader, which would install the `appendBuffer` hook too late. The content script is an IIFE too (content scripts cannot be ES modules); the service worker is an ES module; the popup is a normal Vite HTML build (`vite.config.ts`).
- `public/manifest.json` is copied to `dist/` as is; edit it there. `vite build` alone builds only the popup: use `pnpm build`.

## Project layout

- `src/page/` MAIN-world page script (hooks the audio, posts it with `window.postMessage`; serves the CC-menu caption track).
- `src/content/` isolated-world content script (chunking, scheduling, captions).
- `src/background/` service worker (speech-to-text and translation API calls).
- `src/popup/` settings popup (React); `src/components/ui/` shadcn/ui components (add more with `pnpm dlx shadcn@<version> add <name>`, then check that imports use `@/lib/utils`).
- `src/shared/` code shared by the entry points: message types (`messages.ts`), settings and `chrome.storage.local` access (`settings.ts`), caption data (`captions.ts`), YouTube URL helpers (`youtube.ts`), the `[yt-ai-subs]` log prefix (`log.ts`).
- Pure logic lives in its own module with a `*.test.ts` next to it (Vitest, Node environment, no `chrome.*`): WebM parsing, audio coverage, scheduling, segmentation, rate limiting, cache eviction, loudness and quiet cuts (`energy.ts`).
- `src/qa/` offline caption-quality evaluation, run by `scripts/qa-replay.ts` on debug captures (see the `test-extension-in-browser` skill). Debug captures hold other people's transcripts: they live in `.qa/` (gitignored) or a scratchpad, never in git. Keep browser glue (`index.ts`, `wav.ts`'s decoding, `overlay.ts`) thin. Test fixtures go in `src/test/`.
- `test/ad-skip/` a test-only MV3 extension (plain JS, no build) that mutes, fast-forwards and skips YouTube ads, loaded next to `dist/` in every agent-browser run so ads do not eat test time (the player sends no timedtext requests during an ad). Not part of the product: it is outside `public/`, `pnpm build` never copies it, and the release zip holds only `dist/`.
- `test/fake-groq/` a test-only CDP client (`node`, run on the VM next to agent-browser; it listens on nothing) that answers the service worker's Groq requests with fake replies and chosen `x-ratelimit-*` budgets, to drive the quota levels and the rest of the background without calling Groq (the `test-extension-in-browser` skill).

## Scripts

Run them in the dev container (see the next section).

- `pnpm build` builds the unpacked extension into `dist/` (production, minified).
- `pnpm dev` rebuilds `dist/` on change (development, inline source maps). Reload the extension in `chrome://extensions` (and the YouTube tab) after a rebuild. Changes to `public/manifest.json` need a restart of `pnpm dev`.
- `pnpm typecheck` (`tsc -b`), `pnpm lint` (oxlint), `pnpm format` / `pnpm format:check` (oxfmt).
- `pnpm test` runs the unit tests (Vitest, `vitest.config.ts`).
- `pnpm check` runs typecheck, lint, format:check and test; it must pass before a commit.

## Development environment

- `.devcontainer/` defines a compose-based dev container (service `app`: Node 24, pnpm via corepack, the repo at `/workspaces/yt-ai-subs`, no ports; `pnpm install` on create). Install, build, lint and tests run there, never on the host.
- The build writes the unpacked extension to `dist/`; browser tests load it from the host path of the worktree. How: the `test-extension-in-browser` skill.

## Development workflow

Every change goes through these five steps, in order:

1. **Plan** with the `plan-it` skill: approach, scope and how it will be verified.
2. **Implement** with the `implement-plan` skill, until `pnpm check` and `pnpm build` pass.
3. **Review** the diff with the `review-change` skill (`git diff main...HEAD` plus uncommitted changes). The review is done by Codex `gpt-6.1-sol` at medium reasoning effort, delegated from the working thread in the same worktree (the reviewers `review-change` spawns run as t3 `delegate_task` children with `role: "review"`, `isolation: "shared"`, `target.model: "gpt-6.1-sol"` and medium reasoning effort; settle them once they report); it reports findings only and does not edit files. Fix what it finds; re-run the review only after large changes.
4. **Verify** in a real browser: install the built extension with agent-browser and check the effect on a YouTube page (the `test-extension-in-browser` skill; keep evidence with the `verification-evidence` skill).
5. **Merge through a pull request**: push the branch and open a PR with `gh pr create --base main` (the body says what changed and how it was verified, and ends with `🤖 Generated with [Claude Code](https://claude.com/claude-code)`). When the CI workflow (`.github/workflows/ci.yml`: `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm build`) passes, merge with `gh pr merge --merge --delete-branch`; if it fails, fix and push to the same PR. Never push to `main` directly. t3 settles the thread once the PR is merged. Step by step: the `ship-pr` skill. Publishing a downloadable version: the `release-extension` skill.

## Secrets

- API keys live only in `chrome.storage.local` of the browser profile. Never commit, log or print a key. For local testing the user supplied the Groq key once through T3's secret prompt; it is kept outside the repo in `/home/dev/.local/state/yt-ai-subs/groq-key` (mode 600) on the dev VM. Use that file as the `test-extension-in-browser` skill says (section 5); do not ask for the key again with `request_secret`. Agents must not read its value into their output: no `cat`, no printing, no command-line arguments, no logs.
